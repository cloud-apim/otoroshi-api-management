# Install

## One binary, five roles

The product is a single Bun program, started with a comma-separated list of roles in `APIM_ROLES`
(default: the first four). A deployment can carry every role, or split them according to load and
exposure — the public portal and the ingester do not have the same profile as the console.

| Role | Serves |
|---|---|
| `api` | `/api` — the admin API, bearer tokens |
| `backoffice` | `/backoffice` (the console) and `/backoffice/api` (the same admin API, with a session) |
| `portal` | `/<workspace>/` and `/<workspace>/front/api` — or `<workspace>.<domain>/` in hostname mode |
| `ingester` | `/ingest` |
| `controller` | no route: reconciles the [Kubernetes resources](./gitops/kubernetes.mdx) of the product — not a default role |

`/health` answers `{"status":"ok","roles":[…]}` on every instance.

The background workers — the projection queue, the periodic drift detection, the remote catalog
scheduler, the payments — run on instances carrying `api` or `backoffice`, unless
`APIM_WORKERS_ENABLED=false`; the rollups and the retention of the analytics run on the instances
carrying `ingester`, one at a time.

## The executable

The product compiles into **one executable**: the server and its roles, the console and the portal
(their files embedded), the migrations, and the command line. It needs nothing beside it but the
two PostgreSQL databases, Otoroshi, and `git` for the git remote catalogs.

```bash
mise run build:binary          # dist/bin/otoroshi-apim, for this machine
mise run build:binaries        # dist/bin/otoroshi-apim-{linux,darwin}-{x64,arm64}
```

```bash
otoroshi-apim                  # the server, with the roles of APIM_ROLES — or: otoroshi-apim serve
otoroshi-apim version
otoroshi-apim apis list default        # the command line: the same commands as bun cli/apim.js
```

Cross-compiling makes bun download the runtime of each target. `mise run test:binary` starts the
executable away from the repository and checks its faces, its health and its command line.

## The container image

```bash
docker build -t otoroshi-api-management .
docker run -p 9000:9000 \
  -e APIM_DATABASE_URL=postgres://… -e APIM_ANALYTICS_DATABASE_URL=postgres://… \
  -e OTOROSHI_URL=http://otoroshi:8080 -e OTOROSHI_CLIENT_ID=… -e OTOROSHI_CLIENT_SECRET=… \
  otoroshi-api-management
```

The image builds both UIs in a first stage and carries `git`, used by the git
[remote catalogs](./gitops/remote-catalogs.mdx).

## On Kubernetes

Two ways, the same resources: the product (its four serving roles, several replicas), its
controller (one replica), and the custom resources it reconciles.

**Kustomize**, with `kubectl` alone:

```bash
kubectl create namespace apim
kubectl -n apim apply -f deploy/kubernetes/secret.example.yaml   # edited: databases, Otoroshi key, tokens
kubectl apply -k deploy/kubernetes/base                          # edit configmap.yaml first, or overlay it
```

`deploy/kubernetes/base` holds the CRDs, a `ConfigMap` of what is not secret, the deployments of
the product and of its controller, their service accounts, the `ClusterRole` of the controller and
the service. An overlay changes the namespace (`apim` by default), the image and the
configuration.

**Helm**, the chart `deploy/helm/otoroshi-api-management`:

```bash
helm install apim deploy/helm/otoroshi-api-management -n apim --create-namespace \
  --set config.publicUrl=https://apim.example.com \
  --set config.otoroshi.url=http://otoroshi-api.otoroshi.svc.cluster.local:8080 \
  --set secrets.existingSecret=otoroshi-api-management
```

Its values follow the variables of the configuration below: `config.*` for what is not secret,
`secrets.*` (or `secrets.existingSecret`, a `Secret` with the keys of `secret.example.yaml`),
`controller.enabled`, `ingress.*`. The CRDs are in its `crds/` folder: Helm installs them first.

The databases are not part of either: point the product at a managed PostgreSQL, or at one you run
in the cluster.

## Databases

Two PostgreSQL databases: the **application data** (workspaces, APIs, drafts, snapshots,
subscriptions, audit…) and the **events and analytics**. They do not have the same write profile,
retention or criticality, so they are two connection URLs — they may live on the same server.
Migrations run at startup.

## Configuration

Installation-level settings come from the environment. Everything per workspace lives in the
database. The gateway connection and the console authentication can also be edited later from the
console (*Gateway* and *Global settings*); stored values take precedence.

### Server

| Variable | Default | Meaning |
|---|---|---|
| `APIM_PORT` (or `PORT`) | `9000` | listening port |
| `APIM_ROLES` | `ingester,api,backoffice,portal` | roles of this instance |
| `APIM_PUBLIC_URL` | `http://localhost:<port>` | public base url of the product |
| `APIM_INSTALLATION_NAME` | the host of `APIM_PUBLIC_URL` | the name of this installation — an environment: `recette`, `production`. A [promoted](./gitops/promotion.mdx) snapshot says where it comes from |
| `APIM_DATABASE_URL` | `postgres://apim:apim@localhost:5442/apim` | application database |
| `APIM_ANALYTICS_DATABASE_URL` | `postgres://apim:apim@localhost:5442/apim_analytics` | events and analytics database |
| `APIM_WORKERS_ENABLED` | `true` | run the projection queue, drift detection and catalog scheduler |
| `APIM_PROJECTION_INTERVAL_MS` | `2000` | how often the projection queue is polled |
| `APIM_DRIFT_INTERVAL_MS` | `60000` | how often drift is detected |
| `APIM_COOKIE_SECURE` | `false` | mark session cookies `Secure` |

### Bootstrap

| Variable | Default | Meaning |
|---|---|---|
| `APIM_BOOTSTRAP_ADMINS` | `admin@otoroshi.io` | comma-separated emails of the installation administrators |
| `APIM_BOOTSTRAP_PASSWORD` | `password` | their local password, set when they are created |
| `APIM_BOOTSTRAP_WORKSPACE` | `default` | slug of the workspace created on first start, and the target of `/` |
| `APIM_ADMIN_TOKEN` | `apim-admin-token` | a static admin API token acting as the first bootstrap administrator |

:::warning
Change `APIM_BOOTSTRAP_PASSWORD`, `APIM_ADMIN_TOKEN` and `APIM_INGEST_TOKEN` on anything that is not
your laptop.
:::

### The Otoroshi cluster

One installation drives one Otoroshi cluster, with an administration key.

| Variable | Default | Meaning |
|---|---|---|
| `OTOROSHI_URL` | `http://localhost:8080` | where the product reaches the Otoroshi admin API |
| `OTOROSHI_HOST` | `otoroshi-api.oto.tools` | the `Host` of the admin API |
| `OTOROSHI_CLIENT_ID` / `OTOROSHI_CLIENT_SECRET` | `apim-admin-client` / `apim-admin-secret` | an Otoroshi admin apikey |
| `OTOROSHI_PUBLIC_SCHEME` / `OTOROSHI_PUBLIC_PORT` | `http` / `8080` | how consumers reach the APIs: `<scheme>://<api domain>:<port>` |
| `OTOROSHI_BACKOFFICE_URL` | `http://otoroshi.oto.tools:8080` | used to link a projected entity in the Otoroshi backoffice |

### Ingestion

| Variable | Default | Meaning |
|---|---|---|
| `APIM_INGEST_TOKEN` | `ingest-secret` | the token the data exporter presents to `/ingest` |
| `APIM_INGEST_URL` | — | `/ingest` as the gateway reaches it, used by the exporter helper |
| `APIM_INGEST_STORE_RAW` | `true` | keep the raw path (see [analytics](./gateway/analytics-and-ingester.mdx)); its sampling, the pseudonymisation and the retention are set in the console |
| `APIM_INGEST_RETENTION_MS` | `300000` | how often the ingester rolls the calls up and applies the retention |

### Developer portal

| Variable | Default | Meaning |
|---|---|---|
| `APIM_TENANCY` | `multi` | `multi`: one portal per workspace · `single`: one workspace, its portal at the root, no workspace selector |
| `APIM_PORTAL_EXPOSURE` | `path` | with several workspaces — `path`: `<portal url>/<workspace>/` · `hostname`: `<workspace>.<domain>/` |
| `APIM_PORTAL_DOMAIN` | `portal.oto.tools` | the domain of the hostname mode |
| `APIM_PORTAL_URL` | `APIM_PUBLIC_URL` | the public base of the portals; its scheme and port make the hostname URLs |

### Payments

The paid plans are sold through Stripe Connect: `APIM_PAYMENTS_PROVIDER`, `APIM_STRIPE_SECRET_KEY`,
`APIM_STRIPE_CLIENT_ID`, `APIM_STRIPE_WEBHOOK_SECRET` — see [Payments](./payments.mdx). Off by
default.

| `APIM_OIDC_ISSUER` | — | enables OIDC for the console when set |
| `APIM_OIDC_CLIENT_ID` / `APIM_OIDC_CLIENT_SECRET` | — | the client at the provider |

The command line is `bun cli/apim.js <command>` from the repository, or `otoroshi-apim <command>`
with the executable.

| Variable | Default | Meaning |
|---|---|---|
| `APIM_URL` | `http://localhost:9000` | the product the CLI talks to |

## The data exporter

Analytics need Otoroshi to send its events to the ingester. From the console, **Gateway →
Connection & events → Install / update the exporter**, or:

```bash
curl -X POST http://localhost:9000/api/gateway/exporter \
  -H 'Authorization: Bearer apim-admin-token' -H 'Content-Type: application/json' \
  -d '{"url": "http://apim:9000/ingest"}'
```

It creates (or updates) an Otoroshi `webhook` data exporter with the id `apim_ingester_exporter`,
filtered on `GatewayEvent`, `LLMUsageAudit` and `McpAudit`, sending batches to `/ingest` with
`Authorization: Bearer <APIM_INGEST_TOKEN>`. An exporter is gateway infrastructure: this
helper only creates the one it marks as its own and never touches the others.

## Portal exposure

There is one portal per workspace and **no global portal**. The workspace is always read from
the URL, never from a session, so an API URL means the same thing to everyone. One form for the
whole installation:

| Form | Settings | A portal is served at |
|---|---|---|
| **by root path** (default) | `APIM_PORTAL_EXPOSURE=path` | `https://apis.example.com/<workspace>/` — no wildcard DNS nor certificate. `/` leads to the portal of `APIM_BOOTSTRAP_WORKSPACE` |
| **by hostname** | `APIM_PORTAL_EXPOSURE=hostname`, `APIM_PORTAL_DOMAIN=apis.example.com` | `https://<workspace>.apis.example.com/` — a wildcard DNS entry and a wildcard certificate. The bare domain leads to the portal of `APIM_BOOTSTRAP_WORKSPACE` |
| **one workspace, at the root** | `APIM_TENANCY=single` | `https://apis.example.com/` — no prefix; the console shows no workspace selector |

The portal API follows the same form (`<portal>/front/api`), and the portal assets are always
served under `/_portal/`. The console and the admin API give the URL of each workspace's portal
(`portal_url`), and **Global settings → Workspaces** shows the form in use. `APIM_PORTAL_URL` (by
default `APIM_PUBLIC_URL`) is the public base of the portals: `https://apis.example.com` above.

A single-workspace installation serves `APIM_BOOTSTRAP_WORKSPACE` alone: it refuses to start when
the database holds other workspaces, and creates no other.

### Changing the form

The form changes every public URL — links in documentation, mails, tickets — so choose it at
installation time. If it changes later, the product remembers the forms served before (the last
five, from one start to the next) and **redirects their URLs to the same page in the current form**,
permanently (`301`, `308` for a form or an API call) — but not cached by the browsers, so that
going back to a previous form never loops:

| From | To | Example |
|---|---|---|
| by root path | by hostname | `https://apis.example.com/acme/apis/x` → `https://acme.apis.example.com/apis/x` |
| by hostname | by root path | `https://acme.apis.example.com/apps` → `https://apis.example.com/acme/apps` |
| one workspace | several | `https://apis.example.com/apis/x` → `https://apis.example.com/acme/apis/x` |
| several | one workspace | `https://apis.example.com/acme/apps` → `https://apis.example.com/apps` |

The old hosts have to keep reaching the product for their redirects to be served: keep the DNS
entries and certificates of the previous form for as long as links to it circulate.

In the development stack `*.oto.tools` resolves to `127.0.0.1`: with `APIM_PORTAL_EXPOSURE=hostname`
and the default domain, the portal of `default` is `http://default.portal.oto.tools:9000/`.
