# Admin API

Everything the console does goes through the admin API, without exception: the very
same router is served on two mounts.

| Mount | Authentication | Used by |
|---|---|---|
| `/api` | `Authorization: Bearer <token>` | the CLI, CI, scripts |
| `/backoffice/api` | the console's session cookie (mutations must be JSON) | the console |

So a feature cannot exist only on screen: *every action of the console replays from the CLI*.

## Tokens

- **Personal tokens**: in the console, **user menu → API tokens**, or `POST /api/me/tokens`
  (`{"name": "ci"}`). The token is shown once; it acts as its owner, with its rights.
- **The bootstrap token**: `APIM_ADMIN_TOKEN` acts as the first bootstrap administrator.

```bash
curl -H 'Authorization: Bearer apim-admin-token' http://localhost:9000/api/me
```

Errors are JSON: `{"error": "…", "details": …}` with a meaningful status (`400`, `401`, `403`,
`404`, `409`). A draft that cannot be published answers `400` with the validation errors in
`details.errors`.

## Trying a request

`POST …/apis/<api>/test` sends a request through the API on the gateway — its real routing, plans,
quotas and keys — with Otoroshi's request tester: `{"method": "GET", "path": "/search", "query":
"q=x", "headers": {…}, "body": "…", "subscription_id": "sub_…"}`, the credentials of a
subscription the caller can see when it names one. The answer holds the response (`status`,
`headers`, `body`) and its **execution trace**: the consumer the plans identified (`client_id`,
`plan_id`), then each step that ran plugins, each plugin `allowed`, `denied` (with its status),
`successful` or `failure`, and its duration — which plan recognised the caller, and what refused
it. The request is sent by the gateway itself, from `127.0.0.1`: a keyless plan identifies it by
that address. The raw report of the gateway is never answered: it holds the headers of the request,
credentials included.

## Paged lists

The lists that grow — the audit trail (`GET …/audit`, `GET /audit`), the request log
(`GET …/analytics/calls`), the task queue (`GET /gateway/tasks`) and the people (`GET /users`, searched
by email, name and tags) — are searched and paged on the
server: `?q=` (free text), `?limit=` (up to 500) and `?offset=`, answered as
`{ "items": […], "total": 1234, "limit": 50, "offset": 0 }`. The same parameters search and page the
deployment history of an api (`GET …/apis/<api>/deployments`: `history` and `total`), the usage billed
for a subscription (`GET …/subscriptions/<sub>/usage`: `reports` and `total`, the sums over every
batch) and the security events (`GET …/analytics/security`: `items` and `total` follow the search,
`events` and the breakdowns follow the filters only). The other lists are answered whole; the console
and the portal search and page every list, in the url so a filtered list is a link — or, in a modal
or a drawer, in the list itself.

## A complete flow

```bash
H='Authorization: Bearer apim-admin-token'; J='Content-Type: application/json'
B=http://localhost:9000/api/workspaces/default

curl -s -H "$H" -H "$J" -X POST $B/apis \
  -d '{"name": "Books", "version": "1.0.0", "domain": "books.oto.tools", "contextPath": "/v1"}'
curl -s -H "$H" -H "$J" -X POST $B/apis/books/publish -d '{"comment": "first", "deploy": true}'
curl -s -H "$H" -H "$J" -X POST $B/applications -d '{"name": "My app", "team_id": "<team id>", "shared_credential": true}'
curl -s -H "$H" -H "$J" -X POST $B/subscriptions \
  -d '{"api_id": "<api id>", "plan_id": "<plan id>", "application_id": "<app id>"}'
curl -s -H "$H" $B/subscriptions/<sub id>          # the credentials
```

## Audit trail

The admin API writes the audit trail itself: every write, plus the reads that touch secrets or
personal data — credentials, request logs. **Console → Audit**, `GET …/audit?action=api.`, or
`otoroshi-apim audit default`.

### Audit exporters

**Global settings → Audit export**, or the admin API. The trail leaves the product in batches, to a SIEM or a log pipeline, like Otoroshi's data
exporters do for its events. An exporter (installation administrators) posts JSON arrays of
`ApimAuditEvent` to a URL, optionally restricted to a workspace and to action prefixes
(`subscription.`, `credential.read`…), with custom headers. Each exporter keeps a cursor: delivery is
at least once, in order, and nothing is lost while the target is down — the batch is sent again at
the next tick. A new exporter starts from now on, unless created with `"from_beginning": true`.

```bash
curl -X POST http://localhost:9000/api/audit/exporters \
  -H 'Authorization: Bearer apim-admin-token' -H 'Content-Type: application/json' \
  -d '{"name": "siem", "url": "https://siem.example.com/ingest", "actions": ["subscription.", "credential."]}'
```

`GET /audit/exporters` lists them with their lag; `POST /audit/exporters/<id>/test` sends a test
event.

## Export and import

`GET …/export` returns the whole workspace — teams, every API (one document per API-version, with
its documentation pages and snapshot history), applications and subscriptions — and `POST …/import`
re-imports it elsewhere. Import is idempotent: objects are upserted by id, snapshots are
never rewritten, and nothing is deployed.
