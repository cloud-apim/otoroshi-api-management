# Analytics and the ingester

The ingester receives the events Otoroshi exports — `GatewayEvent`, `LLMUsageAudit`, `McpAudit`
and the `CloudApimSecurityEvent` of the Threat Protection Suite — and stores them twice, for two
purposes. Install the exporter as described
in [Install](../install.mdx#the-data-exporter).

## `/ingest`

```http
POST /ingest
Authorization: Bearer <APIM_INGEST_TOKEN>

[ { "@type": "GatewayEvent", … }, … ]
```

The token is also accepted as an `X-Apim-Ingest-Token` header or a `token` query parameter. The body
is a JSON array, a single event, `{ "events": [ … ] }`, or newline-delimited JSON.

## The computed path — mandatory, exhaustive

Every `GatewayEvent` becomes one row, **attributed to the catalogue at ingestion**: workspace, API,
plan, subscription, application, client id, method, path, status, duration, gateway overhead,
backend duration, bytes in and out, error flag, caller IP and user agent.

A `GatewayEvent` names the api, the plan and the subscription of the key that called — its
`identity.apiRef`, as the key said it at the time of the call — and the ingester attributes the
call from it: the api, the plan, and the subscription with its application. A consumer a `keyless`
plan identified has a plan and no subscription. An event without `apiRef` (an AI audit) is
attributed from the client id of a credential the product holds.

On an API with several plans, a plan that does not identify the caller sends an error event of its
own for a call that then succeeds ([G-22](../otoroshi-gaps.mdx)): the dashboards count it as a
call, and as an error.

A quota consumed, an attribution, a token count are **counted, never sampled**. `LLMUsageAudit` and
`McpAudit` go to an AI usage table (provider, model, tool, tokens, cost): collected from day one,
even though AI and MCP products are not in this version — a feature can come later, uncollected data
is lost.

## The raw path — optional, sampled

When enabled (`APIM_INGEST_STORE_RAW`, or **Gateway → Ingestion**), events are also kept as they
came, for diagnosis and export — sampled, lightened and masked:

- **a share of the requests** (100 % by default), decided by request, so that the events of one
  request are kept together; **every error** (status ≥ 400) is kept whatever the share, unless told
  otherwise. Only the raw path is sampled: the computed one counts everything;
- the heavy embedded configurations are dropped (route, descriptor, JWT verifier): only the route's
  id, name and metadata remain; the headers can be left out too;
- **secrets in the URL are masked**. Otoroshi already masks credential headers and secret fields of
  configurations; nothing masks a secret passed in a query parameter, so the ingester does it:

```
http://books.oto.tools:8080/v1/books?page=1&api_key=leaked-secret
http://books.oto.tools:8080/v1/books?page=1&api_key=********
```

Parameters whose names look like a secret (`*token*`, `*secret*`, `*password*`, `api_key`, `key`,
`sig`, `signature`, `code`, `auth*`…) are masked.

## Personal data — pseudonymised before they are stored

An event names people: the address of the caller, the user signed in on the gateway, its browser,
sometimes a path (`/users/jane@example.com/orders/42`). **Gateway → Ingestion › Personal data** says
what becomes of them, **before anything is stored, in both paths**:

| | by default | otherwise |
|---|---|---|
| **Address of the caller** — `from`, and the headers that carry it (`X-Forwarded-For`, `X-Real-IP`, `Forwarded`…) | truncated to its network (`/24`, `/48`) | kept, replaced by a pseudonym, or left out |
| **Signed-in user** — its email and name (a private app) | replaced by a pseudonym | kept, or left out |
| **User agent** | kept | left out |
| **Paths** | kept | templated: `/users/{email}/orders/{n}`, the values of the query left out |

By default the product keeps the least that still serves: a network is enough to see where the
traffic comes from, a pseudonym enough to count the calls of a user.

A **pseudonym** is a keyed hash (HMAC-SHA-256): one caller, one token — calls can still be counted
by caller — never the address back without the key. The product makes the key, keeps it, and never
shows nor exports it; **rotating** it breaks the link between the pseudonyms before and after. The
client id of an application is not personal data: it stays, it is what attributes a call. The
geolocation and the parsed user agent go with the address and the agent.

A change applies to what is received from then on. Every change of the policy is in the audit
trail, with its values before and after.

Otoroshi exports the events whole — other uses need them — and leaves masking, pseudonymising and
sampling to whoever stores them ([G-19](../otoroshi-gaps.mdx)): what reaches the ingester has the
personal data in clear, over the exporter's connection.

### Security events

The Threat Protection Suite sends one normalised event per decision, `CloudApimSecurityEvent`
(category, action, outcome, severity, score, the caller, the route and its api, an incident). The
ingester keeps it in a table of its own, attributed like the calls: the API from the event, and the
plan, the subscription and the application from the key that called. A keyless caller, or one
refused before it was identified, has the API only: the event does not carry the plan
([G-26](../otoroshi-gaps.mdx)). The address of the caller is pseudonymised like the calls'; the
events are kept as long as the calls.

## Rollups and retention

The calls are kept **30 days**. Before they go, they are **rolled up by the hour**: one row per hour,
workspace, API, plan, subscription, application, method, templated path and status class — calls,
errors, durations (their sum and a histogram), gateway overhead, bytes. The rollups are kept
**400 days**; the AI usage 90 days, its tokens rolled up by the hour too; the raw path **7 days**.
Every duration is set in **Gateway → Ingestion › Retention**.

The rollups are made by the ingester every five minutes (`APIM_INGEST_RETENTION_MS`), one ingester
at a time, **by id, not by hour**: a late event is counted in its hour, and nothing is counted twice.
A call is deleted only once rolled up. **Roll up and purge now** runs it at once.

A dashboard whose range starts after the last purge reads the calls themselves, exactly. Before,
it reads the rollups plus the calls not rolled up yet: its **counts are exact**, its buckets an hour
at least, its percentiles read from the histograms (an approximation, marked `≈`), its paths
templated. The request log is the calls: it goes back as far as they are kept.

## Dashboards

They speak the catalogue's vocabulary — APIs, plans, applications — not the infrastructure's.

- **Console → Observability**, and the *Analytics* tab of each API and application. One row of
  filters scopes everything below it, and lives in the URL, so a filtered view is a bookmark: the
  timeframe — from the last 5 minutes to the last year, or a custom range — the API, its plan, the
  application, the status class (2xx to 5xx); a refresh, and an auto-refresh every 10 seconds to 5
  minutes.
  - **The figures**: calls and the applications that made them, requests per second, errors and
    server errors, latency — average, minimum, maximum, p95 — and the overhead of the gateway, data.
  - **Over time**: the responses, split into successes, client errors (4xx) and server errors (5xx,
    and the failures of the gateway); the latency (average, p95, gateway overhead); the hits of the
    first four applications and APIs, the others folded into one gray line. The buckets follow the
    range — a minute for an hour, a quarter of an hour for a day, an hour for three days, a day for
    three months — and the empty ones are shown: a bucket without calls has no latency, not a zero
    one.
  - **The tops**: APIs by calls, by server errors and by latency; applications by calls and by
    latency; plans; status codes; hosts; endpoints by templated path, and paths as they were called.
  - Every chart has its legend and a table view. **View the logs** opens the request log with the
    same filters.
  A range read from the rollups keeps its counts exact; it has no minimum, no maximum and no
  percentile per bucket, nor the hosts or the paths as they were called — the dashboard says so.
  Reading the request log is recorded in the audit trail: it is personal data.
- **Console → Observability → Logs**: the request log — the calls themselves, as far back as they
  are kept — with the filters of the dashboards, and its own: the method, a part of the path, the
  client id (from a call), a free search (path, status, host, client id, address, request id). A call
  opens on its detail: its request id, host, API, plan, application, client id, address, user agent,
  and where its time went (backend, gateway overhead). **Export as CSV** downloads the filtered calls,
  the most recent first (50,000 at most); a cell a spreadsheet would run as a formula is quoted as
  text. Reading the log and exporting it are recorded in the audit trail (`analytics.calls.read`,
  `analytics.calls.export`): it is personal data. In the admin API:
  `GET …/analytics/calls?status=&method=&path=&client=&plan=` and `GET …/analytics/calls/export`.
- **One request id, end to end.** The gateway gives every call an id, `Otoroshi-Request-Id`: the
  caller gets it back in the response, the backends receive it with the request (the projection
  adds `Otoroshi headers in` to the flows of an API, unless its settings say otherwise:
  **Settings › Correlation**), and the request log keeps it — a request id a consumer or a backend
  quotes finds its call in the search of the request log.
- **Console → Observability → Security**, and the *Analytics* tab of an API whose plans carry the
  threat protection: the security events by category, action and plan, how many were refused or
  masked, the latest ones. Reading them is recorded in the audit trail: they carry the address of
  the caller.
- **Portal → Usage**: the same, restricted to the consumer's own applications.
- **Portal → My apps**: the live quotas of each key, as the gateway counts them (read-only, never on
  the request path).
