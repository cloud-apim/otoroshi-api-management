# Projection

![A deployment always shows its diff first: catalogue changes and gateway changes](/img/screenshots/console-deploy-dry-run.jpg)


The product never enforces anything itself: it **projects** what a published snapshot describes
onto the Otoroshi cluster of the installation, through the Otoroshi Admin API. Only what the
gateway needs to *enforce* is pushed.

## The `Api` entity

Deploying a snapshot writes one Otoroshi `Api` entity, whose id is the product's API id:

```json
{
  "_loc": { "tenant": "default", "teams": ["default"] },
  "kind": "Api",
  "id": "api_01a1eb8054c5…",
  "name": "Books 1.0.0",
  "domain": "books.oto.tools",
  "contextPath": "/v1",
  "state": "published",
  "metadata": {
    "created_by": "remote_catalog=otoroshi-apim-deployment",
    "apim_api_id": "api_01a1eb8054c5…",
    "apim_workspace": "ws_01a1eb8016…",
    "apim_snapshot_id": "snap_01a1eb806b…",
    "apim_snapshot_number": "2"
  },
  "routes": [ … ],      // one per resource
  "backends": [ … ],    // with their client settings
  "flows": [ … ],       // shared policy groups expanded in place
  "plans": [ … ],       // auth kind, rate limiting, restrictions, plan plugins
  "documentation": null
}
```

- **The catalog marker**. Otoroshi treats any `Api` write whose `created_by` starts with
  `remote_catalog=` as the deployment of a catalog: the API may be created already published,
  `production_readonly` is lifted, state transitions are still checked, and the write is recorded in
  Otoroshi's own deployment history (`deployments`, the last five). The product uses the id
  `otoroshi-apim-deployment` — no real remote catalog may use it.
- **Ownership**. The marker and `apim_api_id` are how the product recognises its own
  entities on a gateway that also serves other things — for drift detection, adopt mode and cleanup.
- **No tenancy**. Everything lands in the default location: a workspace is never an
  Otoroshi tenant.

## Derived objects

Otoroshi objects that follow from the description of an API are **derived** by the product:

| Derived from | Otoroshi object | Id |
|---|---|---|
| a `jwt` plan that describes how its tokens are validated | JWT verifier | `apim_jwt_<api>_<plan>` |
| the trusted CAs of an `mtls` plan | certificate (CA, no private key) | `apim_ca_<api>_<plan>_<hash of the certificate>` |
| an `oauth2-remote` plan that describes its authorization server | auth module (`oauth2`) | `apim_auth_<api>_<plan>` |

They are written before the `Api` that references them, marked with the same `created_by` marker
plus `apim_api_id` and `apim_derived`, shown in the deployment diff, compared by drift detection
(on what the product owns: the gateway adds the dates of a certificate, and may not give a secret
back), and removed after the `Api` when no plan derives them any more. What does not follow from an API — the cluster, global
plugins, data exporters, listeners — is infrastructure the product references and never owns.

## Subscriptions and keys

An active subscription is written as an Otoroshi `ApiSubscription`, with the same id as the
product's subscription:

```json
{
  "id": "sub_01a1eb808c84…",
  "status": "enabled",
  "plan_ref": "plan_…",
  "api_ref": "api_…",
  "owner_ref": "app_…",
  "subscription_kind": "apikey",
  "metadata": { "id_ref": "app_…", "apim_subscription_id": "sub_…", "apim_workspace": "ws_…" }
}
```

On `apikey` and `oauth2-local` plans Otoroshi mints the key from the plan's template. The key carries
`apiRef = { api, plan, sub }`, the plan's throttling strategy and restrictions, and the
subscription's metadata — among which **`id_ref`, the application**. That is what answers
"which APIs does this application consume" and "which keys to revoke if it is compromised".

On `jwt`, `mtls` and `oauth2-remote` plans Otoroshi mints no key: the gateway builds the consumer
at each call from the token or the certificate. The `ApiSubscription` then carries the client id
the application declares, as the metadata `apim_client_id`. Otoroshi does not read it yet
([gap G-17](../otoroshi-gaps.mdx)); it is re-projected when the application changes its client id,
and a value changed on the gateway is reported as drift.

A suspended subscription is projected `disabled`; a pending or rejected one is not projected at all;
closing deletes the keys first, then the subscription.

## Asynchronous and replayable

Every projection goes through a task queue. A task is idempotent — it computes the wanted
state and makes the gateway match — and retried with a backoff (2, 4, 8… seconds, at most 5 minutes)
while the gateway is unreachable. A refusal of the gateway (`4xx`) fails it at once; so do 25
attempts. A subscription accepted while the API is not deployed waits, and is projected at the
deployment.

The **Gateway** page of the console shows the queue, and what each task works on. A task that
**failed** — the gateway refused it, or it failed too many times — does not run again by itself:
fix its cause and **retry** it, or **dismiss** it when it no longer applies (an installation
administrator). A failed task whose object is gone — a subscription deleted since, a deployment
of a deleted API — is dismissed by itself, saying why. At the bottom of the sidebar the gateway
pill counts the failed projections (red), the waiting ones (orange) and the drift, and leads to
the first of them. What keeps working while the gateway, or the product, is down:
[When the product is down](./product-down.mdx).

## Never projected

| Stays in the product | Even though Otoroshi has the notion |
|---|---|
| drafts and the snapshot history | Otoroshi `Draft`s and API deployments |
| documentation pages | `ApiDocumentation` |
| catalogue visibility, subscribability, approval workflow | plan visibility and validation labels |
| terms of use, usage statements, request forms | — |
| pricing, payment state | plan pricing |
| [metadata](../concepts/metadata.mdx) | entity metadata |
| workspaces and teams | tenants and teams |

## The escape hatch

*No longer need to* is not *no longer able to*. In **API → Settings → Technical details**
the console shows the Otoroshi entity behind the API, the marker, the gateway's own deployment count,
a link to open it in the Otoroshi backoffice, and the entity exactly as the gateway holds it. The
admin API serves the same at `GET /api/workspaces/<ws>/apis/<api>/projection`: the expected entity,
the actual one and the last drift report.
