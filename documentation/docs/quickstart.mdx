# Quickstart

This walks through the development stack: an Otoroshi gateway (18.1 or later), PostgreSQL, a demo backend and
the product, all in Docker.

## Requirements

- [Bun](https://bun.sh) 1.3 and Docker
- an Otoroshi jar, 18.1 or later: `../otoroshi.jar` relative to the repository by default, or
  `OTOROSHI_JAR=/path/to/otoroshi.jar`

## Start the stack

With [mise](https://mise.jdx.dev/), which also installs Bun and Node:

```bash
mise trust && mise install
mise run install               # dependencies of the product and of the documentation
mise run up                    # builds the uis; starts postgres :5442, otoroshi :8080, echo backend,
                               # dev OIDC provider, catalog source and the product :9000; waits for them
mise run demo                  # demo apis, a gitops workspace with its remote catalog, the data exporter
```

`mise tasks` lists the other tasks (tests, ci, docs, logs, psql, cli…). Without mise:

```bash
bun install
bun run build
docker compose -f docker/docker-compose.yml --profile apim up -d
```

The `apim` service runs your working copy with `bun --watch`: server changes reload by themselves,
UI changes need `bun run build`.

| What | Where | Credentials |
|---|---|---|
| Console | http://localhost:9000/backoffice/ | `admin@otoroshi.io` / `password` |
| Developer portal | http://localhost:9000/default/ | self signup |
| Admin API | http://localhost:9000/api | `Authorization: Bearer apim-admin-token` |
| Otoroshi | http://otoroshi.oto.tools:8080 | `admin@otoroshi.io` / `password` |

`*.oto.tools` resolves to `127.0.0.1`, so the APIs you create are reachable as
`http://<domain>:8080` on your machine.

:::tip Why the product runs inside Docker
The Otoroshi data exporter must reach the ingester. Inside the compose network it reaches
`http://apim:9000/ingest`. Running the product on the host works too (`bun --watch server/main.js`),
but the gateway container then has to reach your host.
:::

## Create an API in the console

1. Sign in, then **APIs → New API**: a name (`Books`), a version (`1.0.0`), an owning team, a domain
   (`books.oto.tools`) and a context path (`/v1`).
2. The API is created as a **draft** with one resource (`/`, all methods) towards the `echo` backend,
   a published `apikey` plan named *Default* and a *Getting started* page in English and French.
3. Click **Publish**: the dialog shows the validation and the changes, and *Publish and deploy*
   freezes snapshot #1 and projects it on the gateway.

The banner of the API page now says that snapshot #1 runs on the gateway.

## Or declare it from a file

```bash
export APIM_TOKEN=apim-admin-token
bun cli/apim.js apply default -f examples/petstore.yaml --publish --deploy
bun cli/apim.js apis list default
```

`examples/petstore.yaml` is a [declarative API document](./gitops/declarative-documents.mdx): two
`apikey` plans, one limited to the `/pets` resource, an OpenAPI specification and a bilingual page.

## Subscribe from the portal

1. Open http://localhost:9000/default/ and **sign up**.
2. Open the API, **Plans → Subscribe**. Choose or create an application (it lands in your personal
   team), answer the usage statement and accept the terms if the plan asks for them.
3. On an automatic plan the subscription is active at once: **My apps** shows the client id and the
   secret.

## Call the API through the gateway

```bash
curl http://books.oto.tools:8080/v1/hello -u "$CLIENT_ID:$CLIENT_SECRET"
```

Without credentials the gateway answers `401`; past the rate limit of the plan, `429`. A new key can
take a few seconds to become routable.

## See the traffic

In the console, **Gateway → Connection & events → Install / update the exporter** creates an
Otoroshi data exporter that sends `GatewayEvent`, the security events of the Threat Protection Suite
and the AI audits of the LLM extension to the ingester.
From then on, **Observability** and the **Usage** page of the portal show calls attributed to the
API, the plan, the subscription and the application.

## Run the tests

```bash
bun test test/model.test.js      # unit tests, no infrastructure
mise run test                    # everything: the interfaces built, then every test against the real gateway
```

The reference catalogue test (`test/reference-catalogue.test.js`) describes a catalogue — 6 plans,
5 auth mechanisms, 4 approval modes on one API and one set of routes — and checks that it is
projected, reconciled, and that its drift is detected and repaired.

The interface test (`test/ui.test.js`) drives the console and the portal in a headless Chromium
(`CHROMIUM`, `/usr/bin/chromium` by default; skipped without one): every page of the console opens
without an error, a producer makes an API and a plan, the console speaks French, a consumer
subscribes from the portal and gets its credentials.
